Check where a site saves pages before using WordPress

This update helps publishers put a page in the right place. It cuts wasted work when a site has changed how it runs. It improves the WordPress publishing task, which turns a checked draft into a page readers can see.

Maintenance record · October 12, 2026

What was wrong

A site can keep WordPress-looking pages and pictures after it starts serving fixed files. A missing login page does not tell us who hosts it. The old recipe named a supported editor, but did not clearly require proof that WordPress was still the right editor.

What changed

The recipe now starts with the site's live state, source of edits and allowed release path. A small table separates live WordPress, static files, other site tools and unknown states. Only a confirmed WordPress route continues to the WordPress steps. Other sites use their maintained release process or keep the exact missing evidence visible.

The first-use prompt, checklist, teaching examples and handoff now follow the same rule. A saved backup origin, source merge or draft preview does not prove that a change is live. Existing release holds remain in place.

How we checked it

The dated source review supports the opening, steps, evidence limits and handoff. The Content Factory link returned an access error, so its availability check remains open. Build, download and public-page checks are separate release steps recorded with this maintenance run. The examples are invented for teaching; they are not customer jobs.

This maintenance work does not publish a client page or prove that a new user can finish setup. The earlier article delivery remains a separate historical record. No additional business run is inferred from reviewing it.

Where it fits

This supports the Post stage of the Content Factory: place checked work on the right channel, then verify what readers receive. The article guidelines check the draft before this task.
