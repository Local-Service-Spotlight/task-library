# Maintain a canonical honor and story leaves

You may have a few stories about someone you work with. This guide helps you give them one clear home. Start with the real source and the pages you have.

**The path:** Real shared work → One helpful hub → Distinct story leaves → Checked links both ways.

**Use this when:** New material about a real relationship should improve an existing or justified main honor page and its specific story pages.

## Inputs
- Verified relationship evidence, intended [Goals, Content, and Targeting](https://blitzmetrics.com/gct-business-strategy/) and public/private limits.
- Original recordings/transcripts/photos, media permissions and known identity home.
- An inventory of the existing honor hub, people-directory card and story leaves, with current source revisions.
- Approved site/channel edit scope, source owners and actual next recipient.

## First-run prompt

> Use the real relationship evidence and existing page inventory to improve one canonical honor hub and its distinct stories. Name actual themes, preserve rich URLs, add useful links both ways and verify media/identity. Keep private relationship data out of public copy. Complete only the already-authorized site/distribution actions and record true public or pending states.

## Steps
1. List the existing pages about the relationship and what each does. A people-directory card is not the full honor, and a short person-slug stub does not earn the main role by its URL alone.
2. Choose one helpful canonical relationship page on the relevant site. If it is thin, improve it from real shared work and sources before making claims about its authority. Do not create a competing biography to handle every new recording.
3. Name the real themes or limbs under that hub. Place each distinct tape/story under an appropriate theme. If no theme fits, record the content-placement decision rather than forcing an unrelated story onto the site.
4. Process each useful tape into its own source-faithful story with quotes checked against the transcript. Keep the real scene and lesson; the derivative story is not a second main relationship essay.
5. On each leaf, put the verified source player or meaningful visual early, with the named theme and link to the main hub visible in the first screen. Use the maintained caption/no-autoplay policy and no guessed or known-dead video IDs.
6. Update the hub with a useful summary and inbound link to each leaf under the correct theme. Link the person’s verified entity home. Keep relationship terms proportional to evidence and do not publish private contact data or invented introduction paths.
7. Preserve rich story URLs. Only a true duplicate honor might justify a scoped redirect; do not send a rich story into a thin stub or assume every similar slug should redirect. Verify any authorized redirect’s final target.
8. Save each change through its supported source and check normal canonical desktop/phone views. Reconcile the actual inventory: one hub, named themes, leaf-to-hub and hub-to-leaf links, source IDs and any pending external-site edit.
9. Use only the distribution destinations in the existing plan. Another person’s site or audience is not ours to edit from a relationship claim. If an intake monitor is requested, use a real watermark, duplicate check, quiet no-change path and named first-firing owner; do not install one for every honor page.
10. Write the run’s meta with the actual changed pages, proof and remaining work. Hand the useful public pages or staged changes to the next owner, with promotion reserved for the separate evidence-based scope.

## Definition of done (QA checklist)

- [ ] There is one useful relationship hub and distinct preserved stories, not competing masters.
- [ ] Each leaf names its theme and links the hub early; the hub links the real leaf and entity home.
- [ ] Evidence, media IDs, privacy and relationship wording are verified.
- [ ] The actual save/public state and inventory reconcile; no unasked redirects, outreach or scheduler are inferred.

## Example(s)

**Fictional teaching example — no real relationship or site edit.** A sample business owner has one page about working with a local mechanic and two stories: a shop visit and a photo-checklist lesson. The main page describes the actual shared work. The visit story remains about that visit; it links up under “Shop visits.” The checklist story links up under “Customer education.”

The hub links both leaves and the mechanic’s verified business home. It does not call the mechanic a partner or friend unless the real evidence supports that wording. No rich story is redirected into the hub merely to reduce the URL count.

## When this runs

For new relevant source material or a scoped repair to the honor tree. Optional phone/source intake needs its own real configured cadence; no universal daily scan is created.

## First-run setup and continuity

Open the supplied task file and its linked source. Verify the project’s real inputs, account, access and output folder before work. This Markdown file is a guide; it does not install an app, connect an account, supply a subscription or create a schedule. Carry out work already authorized; do not ask for the same approval again. Keep any unsupplied destination or new action outside that scope clearly pending.

Save source IDs, versions, decisions, checked outputs and next owner in the project tracker. Before a retry, check the saved state and other workers’ changes. A model name does not guarantee memory or a running timer. Repeated work needs an actual configured trigger and durable state; one-off work can be started by the prompt above.

Keep agent media muted with volume zero before playback. If mute cannot be verified, use captions, metadata or still frames. State the limit: silent visual checks do not prove spoken-word accuracy or audio quality. Do not start sound through the user’s speakers unless explicitly asked.
