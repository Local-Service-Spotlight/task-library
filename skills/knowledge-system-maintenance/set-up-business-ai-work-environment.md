# Set up a business AI work environment

You do not need a whole system to try useful AI work. This guide helps you set up one task with the right files and checks. Start with a small draft you can judge before you share it.

**The path:** Useful first task → Supported app → Needed access → Checked result

**Start when:** A business owner has chosen a useful first AI task and needs the smallest supported setup for it.

## Inputs

- A real business need, bounded first draft and pass criteria.
- The selected computer/app/account/plan and current supported capabilities.
- Allowed source files and scope for installing tools or connecting accounts.

## Steps

1. Choose the first task and record what useful output looks like. Start with safe provided files when possible; a public website read does not require a publishing connection.
2. Use the maintained install guide to select the supported product path. Confirm the actual surface/plan, rather than assuming every app has Cowork, local folders or marketplace controls.
3. Install or load the intended skill through [the canonical installation task](https://local-service-spotlight.github.io/task-library/?task=install-canonical-skill-packs#task-install-canonical-skill-packs). Record the exact source and verify actual selection in a fresh task.
4. Connect only sources the task requires, through existing approved connectors or credential handling. Test the narrow needed action; read access, draft access and publish access are different.
5. If a site connection must be tested, prefer a non-public draft where that proves the required capability. A public test and its cleanup require that exact authority; do not publish a dummy post just because a general setup guide says so.
6. Run the bounded task, inspect the saved output against the agreed checks, and record any access/capability gap. Keep the result available to the intended reader.
7. Only after the task works, decide whether repeat work is needed. Configure and observe any schedule through its separate task; a manual first result can finish a one-off setup.

## Definition of done (QA checklist)

[Quality assurance (QA)](https://localservicespotlight.com/article-guidelines/) means checking the work against the agreed result.

- [ ] Chosen app and skill support the actual task; source/revision and selection are recorded.
- [ ] Only necessary access is used and each required action is checked.
- [ ] A useful first output or precise blocker is retained; scheduling is not assumed.

A fictional shop owner wants draft answers to common questions from an approved service sheet. The first task needs that file and a writing skill, not website publishing access. The draft is checked against the sheet and saved. A recurring web-publishing system remains separate future scope.

## Run with an agent

Give the AI worker this recipe, the real Inputs above, the intended result and the actions already authorized. Ask it to return the saved output, checks, evidence and remaining owner. Check its work against this guide; loading a skill does not prove access, installation of a job, or successful execution. Keep media muted with volume at zero if playback is needed.

For recurring work, keep the actual trigger, owner and runtime in the job record. Scheduling and observed firings are separate. Do not create a schedule merely because this guide mentions a review interval.

## Record the real execution

Open the run record when the work starts. Keep the exact starting recipe revision, one execution ID, source evidence and actual state. Write a [meta article, the record of one run](https://blitzmetrics.com/meta-article-prompt/) with decisions, results, checks, failures and next owner. Link it to this task and register it through the [Task Library](https://local-service-spotlight.github.io/task-library/) execution process. Writing is part of the work; public release follows existing authority.

Reuse the same execution ID for revisions, QA, meta writing and retries within that run. A blocked run stays open with its dependency and next owner; do not invent a finish time. Use supported findings to propose and verify a better recipe. A historical public-example count without distinct run IDs remains dated article volume, not verified execution frequency.
