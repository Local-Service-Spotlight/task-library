# Route notes to task guide Update Protocol or directly to articles

A saved lesson still needs to reach the right guide. This task helps you choose whether to add proof or change the steps. Start with the note, its source, and the page that owns the subject.

**The path:** Saved lesson → Check source → Choose route → Record outcome

**Start when:** A saved lesson has been captured and still needs a verified destination and next owner.

## Inputs

- [Capture a lesson within 24 hours](https://local-service-spotlight.github.io/task-library/?task=generate-knowledge-capture-note-within-24-hours#task-generate-knowledge-capture-note-within-24-hours) output: source, insight, destination and priority.
- The current topic/page map, article editor and proposal queue.
- A routing owner, agreed review interval and existing authority for changes.

## Steps

1. Read the current unrouted-note list within the agreed scope. Check source access, note identity, duplicate versions and priority. Urgent work can be escalated through existing authority rather than waiting for a routine batch.
2. Check the insight against its evidence and confirm which maintained guide owns it. A capturer’s guessed destination is a starting point, not authority.
3. If it changes how work should be done, route to [Draft a process-change proposal](https://local-service-spotlight.github.io/task-library/?task=create-sop-amendment-proposal-500-words#task-create-sop-amendment-proposal-500-words). Keep at least two real examples for that formal proposal or mark the missing evidence; do not invent a second occurrence.
4. If it adds a fact or example without changing method, prepare an addition to the owning article with a relevance note and source. Use current writing/privacy standards and the supported publishing rail.
5. Record routed, awaiting evidence, proposed, saved draft or published accurately, with destination, owner and date. “Routed” does not mean the guide changed.
6. Check the receiver can find the note/proposal. Revisit parked notes at the agreed review point and escalate repeated blockage; do not silently abandon them or create duplicate notes to clear a queue.

## Definition of done (QA checklist)

[Quality assurance (QA)](https://localservicespotlight.com/article-guidelines/) means checking the work against the agreed result.

- [ ] Every in-scope note has a verified destination or a specific open question.
- [ ] Method and evidence additions take the correct review route.
- [ ] Source, owner, date and actual downstream state remain inspectable.

## Run with an agent

Give the AI worker this recipe, the real Inputs above, the intended result and the actions already authorized. Ask it to return the saved output, checks, evidence and remaining owner. Check its work against this guide; loading a skill does not prove access, installation of a job, or successful execution. Keep media muted with volume at zero if playback is needed.

For recurring work, keep the actual trigger, owner and runtime in the job record. Scheduling and observed firings are separate. Do not create a schedule merely because this guide mentions a review interval.

## Record the real execution

Open the run record when the work starts. Keep the exact starting recipe revision, one execution ID, source evidence and actual state. Write a [meta article, the record of one run](https://blitzmetrics.com/meta-article-prompt/) with decisions, results, checks, failures and next owner. Link it to this task and register it through the [Task Library](https://local-service-spotlight.github.io/task-library/) execution process. Writing is part of the work; public release follows existing authority.

Reuse the same execution ID for revisions, QA, meta writing and retries within that run. A blocked run stays open with its dependency and next owner; do not invent a finish time. Use supported findings to propose and verify a better recipe. A historical public-example count without distinct run IDs remains dated article volume, not verified execution frequency.
