# Set up a Special Project workspace

A free project still needs a clear goal and owner. This guide sets up a shared place for the work, files, and next steps. Start with the approved scope and the people who should take part.

**The path:** Approved scope → Project record → Working threads → Checked access

**Start when:** The relationship owner has confirmed Special Project status, scope and participants.

## Inputs

- The relationship owner’s approved Special Project scope and current roster status.
- The exact existing conversation/project, participant list and accountable lead.
- Authorized project setup/access plus the current Basecamp workflow.

## Steps

1. Confirm Special Project status from the roster and owner. A friendly name, old project prefix or lack of invoice does not authorize unpaid work or change a client’s status.
2. Search for the existing workspace before creating one. For a new approved project, use “Special Project: [real person or company]” with the actual confirmed subject; preserve any established project ID.
3. Enable or use the approved Message Board, To-dos and Docs & Files. Create or locate Project Overview, Access, Updates, Updates (Internal) and Meetings.
4. Write the overview with purpose, scope, deliverables and named responsibility. Use the maintained labels Project Lead, Project Manager and Accountable when the current workflow requires them, matching actual project members.
5. Invite only the confirmed participants under existing authority. Historical named staff in the public article are examples to verify, not a blanket current invite list.
6. Check each thread’s actual client visibility. Keep private team notes in the internal destination and secret values in the approved store, not an Access-thread plaintext dump.
7. Run the applicable access checklist for the work: source systems, site and measurement access as needed. Record granted, missing and untested separately; then assign the first concrete task and verify the receiver can find it.

## Definition of done (QA checklist)

[Quality assurance (QA)](https://localservicespotlight.com/article-guidelines/) means checking the work against the agreed result.

- [ ] Roster state, scope and accountable owner are confirmed.
- [ ] Required threads exist with checked participant visibility.
- [ ] First task and needed access are usable, or exact missing grants have owners.
