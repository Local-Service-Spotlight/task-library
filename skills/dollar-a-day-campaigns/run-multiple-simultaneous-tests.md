# Run multiple simultaneous tests

You want to learn which post or group is a better fit. This guide helps you plan a few small tests at once. Start with one clear question and the total amount you can use.

**The path:** One question → priced test rows → bounded runs → fair review.

**Use this when:** More than one proven creative or audience hypothesis is ready and the budget and review capacity support parallel tests.

## Inputs
- Qualified posts, reviewed audience rows, a common goal and target; enough evidence to define a useful comparison.
- Exact account/currency/time zone, permitted budget controls, approved total amount and dates.
- Access for the planned actions and a shared log of active tests, remaining commitments, safety rules and review owner.

## First-run prompt

> Build a small test matrix for this question and total budget. Keep each row identifiable, priced and due for review. Compare one planned variable at a time, note overlap, and carry out only authorized launches. Do not create a fixed quota of tests or add budget to make an unsupported minimum fit.

## Steps
1. Choose the question first: two eligible posts with the same audience, or the same post with two audience settings. Do not change the goal, creative, audience and landing page together and call the result an explanation of one factor.
2. Start with only as many rows as the budget and reviewer can handle. The core method can layer one post per day; parallel testing is an option, not a requirement to launch 10–30 cells at once.
3. Create a row for every planned test with source post ID, audience, goal, budget type, amount, start/end times and success rule. Where Google Ads is used, budget belongs to the campaign; do not pretend each ad group has an independent cap.
4. Price the whole plan before launch. Three nominal $1/day tests for seven days mean $21, not $7. Verify platform minimums, average-versus-total behavior, fees and true limits; fewer tests or a pending plan is better than an unapproved increase.
5. Check shared/campaign budget behavior. If the chosen setup can move money across rows, report that allocation limit. Separate settings alone do not guarantee equal spend or a randomized experiment.
6. Inspect previews and saved settings, then launch only within the existing authority. Read back all IDs, dates and budgets. On a retry, reconcile the log first so the same row is not launched twice.
7. Check early delivery, broken links, missing events and ceiling drift. Avoid unnecessary changes during the planned window, but apply already authorized protective stops. Record any change and its date.
8. Review each row after its own full window. For staggered launches, due dates differ. Compare matching metrics, note sample and auction limits, and send every row to a keep, stop or bounded hold decision.

## Definition of done (QA checklist)

- [ ] The matrix answers one clear question with identified source posts.
- [ ] All row commitments fit the actual authorized total and current platform controls.
- [ ] Independent budgets are not claimed where allocation is pooled.
- [ ] Launch/retry checks prevent duplicate active rows and record early issues.
- [ ] Every row has its own due date and evidence-qualified verdict.

## Example(s)

**Fictional teaching example:** A shop has $21 for three seven-day tests in a setup that supports the plan. The matrix records three $7 nominal commitments and the actual spend controls. All use one goal, but only A and B compare two clips with the same audience; C explores a different audience and is labeled exploratory. If a row is rejected or receives too little delivery, it is not called a loser from zero results alone. The final report preserves actual spend instead of filling each row with a made-up $7.
