# Execute switch boosts to new audiences

A post worked with one group of people. You want to see if it helps another group too. This guide helps you make that test without losing track of the first result.

**The path:** Proven post → new group → separate test → compare results.

**Use this when:** An existing post has a qualified paid result and a new relevant audience hypothesis fits the available budget.

## Inputs
- Original post/ad IDs, full-window result and pre-set target; current budget/end date of any still-running winner.
- The next audience’s source, fit, allowed settings and eligibility.
- Authority for the specific new test or replacement, aggregate budget ceiling, dates and current account roles.

## First-run prompt

> Prepare a switch-boost test using this verified winning post and the proposed new audience. Keep IDs, budgets and dates separate from the old test. Reuse the original post only where the platform supports it. Act within the provided test scope, then return read-back and the due comparison.

## Steps
1. Recheck that the original qualifies against the written goal, with enough evidence for the proposed next test. A high reaction count alone does not make it a conversion winner.
2. Name why the new audience might benefit from the same content. Use a real service area, relevant interest or eligible warm group. Check any list rights and unsupported settings before preparing the row.
3. Decide whether the scope is an additional test or a replacement. For an additional test, keep the original record and its existing end date unchanged. For a replacement, record the old stop and new start explicitly; neither choice grants extra spending authority.
4. Where supported, select the existing original post and confirm its ID in preview. Do not promise all comments, reactions or placements will carry across accounts or platforms. Label a required new creative as a derivative with its own ID.
5. Keep the creative, goal and planned window comparable while changing the chosen audience variable. Record unavoidable differences such as placement, time, audience overlap or currency; a normal auction comparison is not randomized proof.
6. Price the new test at the method’s $1/day for seven days where feasible. Read current minimums and true spend controls. Add the old and new commitments before any authorized activation.
7. After saving or launching within scope, read back both records. Check the correct post, audience, status, budget and end date. Monitor early delivery; do not edit the original’s audience by accident or duplicate the same active test on a retry.
8. Compare the full windows using the same metric. Keep, stop or hold the new test with a due date. A failure in this audience/window is useful evidence, not proof the post can never work elsewhere.

## Definition of done (QA checklist)

- [ ] The original winner has linked evidence and retains its exact record.
- [ ] New audience fit, rights and available settings are checked.
- [ ] Additional-test versus replacement scope and total cost are explicit.
- [ ] Original-post reuse or a new derivative is verified in preview/read-back.
- [ ] The final comparison includes confounds and a bounded next action.

## Example(s)

**Fictional teaching example:** A repair tip beat its view-cost target in Cedar Town. The shop also serves Maple Town, so the next test uses the same eligible post there. The original still has three days left in its approved run. The log records both commitments before the seven-day Maple test is activated. Maple’s cost is higher, but its run began during a holiday. The report stops that test under its rule and records the timing limit; it does not declare all Maple customers a poor fit.

## When this runs

One new audience hypothesis per bounded test. Batch or recurring switch tests are optional and must fit the existing budget and review capacity; no automatic sequence of paid launches is implied.
