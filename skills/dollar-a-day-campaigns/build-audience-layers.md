# Build audience layers

Your ad needs to reach people who may need your help. This guide helps you choose a few clear groups to test. Start with the place you serve and the problem your post solves.

**The path:** Real buyer need → allowed groups → clear test rows → budget plan.

**Use this when:** Proven content and a goal are ready, and the campaign needs a testable audience plan.

## Inputs
- The actual service area or market, offer, buyer problem and campaign goal.
- Read access to the current platform’s available audience settings, estimates and policy/category requirements.
- Approved first-party audience sources, if used, with the right to use them for advertising; the creative shortlist and total test budget.

## First-run prompt

> Build a small audience plan for this goal and these posts. Name the reason for each group, actual supported settings, size/eligibility evidence and one variable to compare. Distinguish strict controls from suggestions. Do not upload lists, create audiences or launch ads beyond the supplied scope.

## Steps
1. Write the audience in plain terms: who has this need, where the business can serve them, and why this post helps. Begin with actual customer evidence, not a guessed age band such as all homeowners aged 30–65.
2. Read the platform’s current category restrictions for the actual offer. Use supported service-area controls; do not add protected-trait exclusions or work around restrictions on housing, jobs, credit or other restricted ads.
3. Make a broad eligible group inside the real market as one possible baseline. Add only distinct, relevant interest or behavior groups that the account actually offers. Do not force three to five groups if the budget or evidence supports fewer.
4. For warm groups, list the permitted source, time window and current status: website visitors, eligible video viewers or platform engagers. A created audience is not proof it has enough matched people to deliver.
5. Use customer-list or look-alike audiences only when source rights, platform terms and current eligibility are satisfied. Do not scrape or upload private contacts merely because an address is available.
6. Record each setting as a required control, an optional suggestion or unavailable. If an automated audience mode can expand beyond a suggestion, do not label the resulting row an exact interest-only test.
7. Build a table with test ID, audience definition, exclusions actually supported, creative ID, goal, budget and review date. Change one planned variable for a useful comparison, while noting overlap and non-random delivery.
8. Pass the table to the budget task before launch. Keep audience-size estimates dated; they are not guaranteed people reached and cannot be turned into a money budget using an undefined percentage formula.

## Definition of done (QA checklist)

- [ ] Each group has a source-backed reason tied to the offer and service area.
- [ ] Settings reflect actual availability and distinguish controls from suggestions.
- [ ] Warm/list groups have recorded rights and eligibility; missing size is unknown.
- [ ] The table names one comparison variable and overlap limits.
- [ ] The combined budget is checked before any groups are activated.

## Example(s)

**Fictional teaching example:** A repair shop serves one town. Its seat-fix video has earned organic shares. The plan has A: the town with no extra interest suggestion, and B: the same town with an available cycling-interest suggestion. Both use the same post. If the interface can expand B, the report calls it an audience-suggestion test, not delivery only to cyclists. A third row for prior site visitors stays pending because the audience is too small. No emails are uploaded to fill the gap.

## When this runs

Build once for a test plan, then revise when the offer, service area, audience rights or platform options change. Review existing groups as part of the campaign’s agreed check; do not create a separate schedule by default.
