# Manage a group member website request

Keep each member’s site request from getting lost. This guide tracks the facts, the build and the next person’s action in one record. Start with the real request and the group’s shared intake list.

**The path:** One request → Validated facts → Site playbook → Owner action → Verified result

**Start when:** A verified group member submits a website request into the group’s accepted intake process.

## Inputs

- The original intake entry, group/member identity and accepted eligibility rules.
- Current domain, site goal, language, bio, real photos, permissioned proof and public contact preferences.
- The existing shared request record, original conversation, build owner and actual access to those sources.

## Steps

1. Find or create the single request row in the accepted shared intake. Match the member using the agreed identifier and keep staff tests distinct. Do not build a competing tracker or expose a private form response in a public status page.
2. Validate the intended person, actual controlled domain, current site and goal. Check the source folder can really be read and list missing assets precisely. A submitted form or a paid membership does not prove domain control, deployment access or consent to publish every field.
3. Inspect the domain’s current web and mail dependencies before preparing setup instructions. Record the actual authoritative DNS host separately from the registrar. Preserve mail and verification records; no-email on the form is not by itself permission to change nameservers.
4. Hand the checked packet to [Deliver the requested personal site](https://local-service-spotlight.github.io/task-library/?task=deliver-personal-brand-site-from-request#task-deliver-personal-brand-site-from-request). Retain parent ownership of request status and dependencies. The build task prepares the source-backed preview and exact host-specific action instead of asking the member to guess technical settings.
5. Advance only the stage that evidence supports. The existing pipeline includes received, validated, site provisioned, instructions sent, DNS pointed, propagating, live, credentials issued and content loaded. Keep a preview, provisioning receipt, send receipt and final public check distinct; labels alone do not create these events.
6. Keep status in the group’s existing authorized conversation. Prepare external messages as drafts unless sending is already authorized. Put the next action with the actual member, web function or access owner, and retain failures instead of silently skipping to live.
7. Before calling a member’s site complete, verify the real public domain, HTTPS, intended content and retained dependencies. Provisioning or propagation delay alone does not prove success. Issue any permitted access through the secure existing rail, never in a public report.
8. For a new group setup, use a clearly marked authorized test request through the whole path before announcing readiness. A daily scan needs a real configured job, owner, timezone and observed run; this recipe does not activate one or assume the historical 4 a.m. job still exists.
