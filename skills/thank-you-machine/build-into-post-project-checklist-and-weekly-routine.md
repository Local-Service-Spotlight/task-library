# Keep a Simple Thank-You Routine

It is easy to forget to thank people when work gets busy. This guide helps your team keep a small list and follow through. Start with real help from recent work. Finish with clear next steps and proof of what was done.

**The path:** Recent work → choose real thanks → track the next step.

**Use this when:** the team wants a repeatable way to notice good deeds after projects or during an agreed weekly review.

## Inputs

- The team’s existing project closeout checklist and recent work records.
- The gratitude log and the owner of the review.
- The chosen trigger or cadence, time zone, actual task tool and allowed communication scope.

## First-run prompt

> Add a small thank-you review to this workflow. Use real deeds, check for duplicates and name the next owner. Keep the client’s work closeout criteria intact. If a repeat is requested, configure and verify the actual schedule; otherwise save the checklist.

## Steps

1. Read the existing closeout rules and current log. Add a review prompt such as “Did someone help in a way we should acknowledge?” without making public thanks or ad spend a condition of completing unrelated client work.
2. Choose an event trigger or an agreed cadence with the team. Define who reviews, which projects are included and how much effort is useful. Do not invent a compulsory weekly quota of videos.
3. Keep one row per deed with source, person, date, intended audience, next owner and state. States can include note ready, clip checked, draft, sent, posted or no further action; require evidence for the last two.
4. Review recent work and check duplicates before planning a new message. Use [Find a Real Reason to Say Thanks](https://local-service-spotlight.github.io/task-library/?task=identify-thank-you-triggers#task-identify-thank-you-triggers) for each worthwhile event. No new deed can mean no message this week.
5. Choose the lightest suitable form: a private note, short video or approved public post. Carry the person’s preferences forward; do not turn each thank-you into a required promotion campaign.
6. If recurring work is requested, configure it in the actual task tool or agent runtime with owner, time zone, trigger, required access and failure route. Verify the saved configuration and the first actual firing. A checklist or calendar idea alone is not a running schedule.
7. At each review, read existing records before retrying a send. Check exact delivery or post evidence, identify the smallest missing item, and carry open work forward with its owner. A reminder or automated acknowledgment is not proof of human receipt.
8. Periodically check whether the routine helps: real deeds noticed, time spent, pending work and repeated-message errors. Adjust the cadence within scope; do not claim relationships or revenue improved without evidence.

## Definition of done (QA checklist)

- [ ] The thank-you prompt fits the project workflow without changing unrelated closeout criteria.
- [ ] The log has source, deduplication key, state, evidence and next owner.
- [ ] Private and public routes are chosen for the actual event.
- [ ] A requested schedule is verified, or clearly remains a proposal.
- [ ] The report distinguishes planned, sent, posted and received states.
