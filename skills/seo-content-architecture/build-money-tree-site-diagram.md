# Build a Money Tree site diagram

See which parts of your site help people find what you sell. This guide draws a tree from the links your pages really have. Start with your full page list and the offers people can buy.

**The path:** Published URLs + offer list → Measured body links → Tree and text view → Owned fixes

**Start when:** An eligible managed site needs its existing monthly tree rebuild or a specifically authorized structure audit.

## Inputs

- [Inventory pages and their purpose](https://local-service-spotlight.github.io/task-library/?task=step-1-inventory-content-and-establish-gct-per-page#task-step-1-inventory-content-and-establish-gct-per-page) with published posts, pages, content types, current body output, date and crawl coverage.
- The actual home, navigation, services and method pages; canonical targets, previous tree and its count definition.
- The maintained Money Tree renderer/source contract and authorized site scope; private measurements only from connected, verified sources.

## Steps

1. Read the current [Money Tree, a site map whose branch sizes show measured supporting links](https://blitzmetrics.com/money-tree/) procedure and existing renderer contract. Confirm the site is eligible and its owner, publication rail, previous run and scope. Use the real home/domain as trunk, existing audience or offer groups as limbs, real method or buying pages as branches, and off-site identity proof as roots.
2. Fetch all published URLs from the supported source and reconcile with the crawl. Include both WordPress Posts and Pages where present. Use rendered article bodies to expand builder or shortcode links, while retaining the source revision and extraction boundaries; list unreadable or missing pages explicitly.
3. Extract actual internal body links and build an inbound index. Count each published post once per branch even if it links there several times. Keep page-to-page links separate and exclude theme navigation from this leaf count. Normalize only documented equivalent URL forms; do not erase meaningful query parameters blindly.
4. Identify the branches from the site’s current navigation, services and topic owners. Follow and record redirects. Group confirmed aliases with a union of distinct source posts, naming the old paths and duplicates as findings. Similar titles alone do not prove two live offers are the same branch.
5. Generate the dated clickable diagram, matching linked text outline and truthful structured metadata from that same checked data. Branch weight follows the source-defined count; bare branches remain bare. Label a simplified opening view and link directly to the full tree so no omitted branch disappears from the review.
6. Check all in-scope offers are represented, nodes resolve or are clearly held, and the three representations agree. Reproduce counts from the saved snapshot rather than expecting a changing live site to freeze. Review useful labels and coverage at desktop and mobile sizes; decoration must not invent supporting leaves.
7. Prepare the public structural view and authenticated private measurement view separately. Keep client leads, revenue and priorities out of public HTML, hidden data, metadata and alt text. When release is authorized, verify the normal URL against the exact saved source and retain rollback evidence.
8. Record bare branches, split destinations, redirects, broken targets and relevant proof gaps with exact URLs, counts and owners. Use verified comparable revenue only for a revenue ranking; disconnected data remains unknown. Hand the accepted tree and deltas to the existing review owner without creating another schedule.

## Fleet rollout and money-page proof

Keep one current public-safe Money Tree per eligible managed site, using the
existing agent-runtime `money-tree/` renderer, source contracts and accepted
run identity. The actual home/domain is the trunk, buying/service destinations
are branches, and relevant published supporting articles/videos are leaves.
Link real nodes to their canonical destinations and retain unknown branches.
The tree is evidence of site structure; it must never imply unmeasured results.

Each buying page has meaningful relevant proof above the fold, evidence beside
material outcome claims, and relevant proof near its primary buying action.
Use the full tree or its useful branch where it explains the offer, alongside
real project scenes, attributable results and source videos. Give supporting
leaves a relevant buying destination and a practical how-to link when useful.
Keep public wording confident and specific: state the sourced moment once;
remove repeated caveats, internal review scores and unsupported claims.

Public trees contain public structure and content counts only. Private sessions,
leads, bookings, conversion rates, revenue, finances and priorities stay behind
authenticated client access, including alt text, metadata, hidden DOM and JSON-LD.
NOT_CONNECTED is not zero. Preserve the existing roster, site authorization,
CMS/deployment/rollback and public/private gates; a schedule or current recipe
is not a release receipt. Reconcile `monthly-client-money-tree-maa` before adding
any clock. Check priority buying pages and named relationships weekly; rebuild
other eligible site trees monthly through their existing owning function.

## Definition of done (QA checklist)

Quality assurance (QA) means checking the actual result against its agreed requirements. Follow the [Article Guidelines](https://localservicespotlight.com/article-guidelines/).

- [ ] Every scoped offer and topic branch comes from the site, with no invented nodes or missing bare branches.
- [ ] Distinct source-post counts, alias handling, crawl date and extraction boundaries can be reproduced.
- [ ] Public diagram, text and metadata agree; private values are absent from every public representation.
- [ ] Each priority finding has a specific next task and owner; structural counts are not claimed as measured sales.
- [ ] Every branch in the service/navigation scope is represented
- [ ] Counts are reproducible and links resolve or are flagged
- [ ] Diagram, outline and schema agree
- [ ] A simplified opening map states its selection and coverage and leads directly to the complete tree; meaningful groups preserve the scoped tree's actual breadth without invented nodes or decorative leaves
- [ ] Each count states its source-defined measure and date; "published posts linking to this offer" is not presented as all relevant proof, all customers or all published content
- [ ] The first 2–3 sentences explain the reader's situation, why the tree matters and how connecting relevant proof to real offers helps the reader choose a next step; no unmeasured conversion or revenue promise
- [ ] Private metrics never enter public markup
- [ ] Each defect has a destination and next action
- [ ] Record the exact source revision, actual result and evidence; retain failure, partial, blocked and unknown states.
- [ ] Write the execution's meta article and link the canonical task. Publication is a separate action under the current authority.
- [ ] Keep this parent job's internal retries, checks and agent contributions on the same execution ID; derivatives and revisions add no runs. A separately scoped and documented child execution may have its own ID with parentExecutionId, without adding a second completion to this parent recipe.
- [ ] Verify permissions for publishing, sending, spending, scheduling or changing access before that action. A task record does not grant them.
- [ ] The exact output, source revision, reviewer evidence and remaining owner action are saved.
- [ ] For any reader-facing output, the short grade-five opening states the reader’s useful outcome and supporting method or proof. The body delivers that promise; a useful authentic visual appears in the first screen. Retain exact text and quoted reviewer evidence.

## Example(s)

**Fictional teaching example. This is not a client result or proof of a completed run.**

A fictional service site has two offers and five posts. Three distinct posts link to the first offer; none link to the second. One post repeats its link three times, so it still counts once. The tree shows counts of three and zero. Without connected lead data, the team can plan relevant proof links but cannot name either offer the top seller.
