# Build an agency website for a vertical

Does your agency site show whom you help and why they should trust you? This guide helps an owner build a site for one clear trade. Start with the founder’s real story, the work you sell and proof you can use.

**The path:** Market and proof → Nine site parts → Supported build → Public QA.

**Use this when:** a named operator needs an agency site for a defined market under the network’s reviewed agency-site playbook.

## Inputs
- The confirmed agency name, exact domain, market, offer and explicit trade carve-outs from the current project record.
- Verified founder story, real media, actual service methods and client evidence cleared for public use. Current roster/engagement controls scope; the client tracker supplies money/routing facts rather than replacing the roster.
- Authorized site/host access and any actual domain/hosting purchase scope, plus supported deployment and rollback procedures.
- The reviewed network intake destination, accountable receiving owner and current task/relationship records so this build does not duplicate another active worker.

## First-run prompt

> Build the scoped agency site using the current playbook and real supplied proof. Implement its nine relevant components, truthful service-method links and shared network intake. Preserve trade carve-outs and existing authority. Verify ordinary public pages and receipt of the contact path before claiming launch.

## Steps
1. Resolve the exact market, agency identity and allowed trades from the project record. Explain its role: the spotlight site develops industry coverage, the agency serves clients, the founder’s personal site establishes their identity, and client sites provide real proof. Do not invent that all four already exist.
2. Verify or acquire the exact authorized domain and provision through the current supported hosting route. Read the actual price, term, renewal and security choices; the article’s old roughly-eleven-dollar, one-session and four-nameserver example is not a current universal contract. Preserve valid existing hosting and domain protection.
3. Plan the nine components: a real founder hero and clear promise; founder About story; services linked to maintained methods; industries and carve-outs; approved client wall; actual results and reporting anatomy; shared audit intake; entity and measurement setup appropriate to the plan; and the source’s three launch articles on origin, reporting philosophy and method. Mark any evidence gap before writing claims.
4. Build the hero and About page from the founder’s real sources. Keep the opening at grade 5, with a meaningful photo or useful diagram in the first desktop and phone viewport. Use evidence-based scenes and precise relationships; no trophy-name paragraph, invented mentorship or unverified result belongs in the copy.
5. Build service and industry pages around the work actually offered. Link each method to its maintained owned guide and organize the pages with the SEO Tree and public Money Tree where applicable. Add verified client examples only under current scope and permission; private tracker data and inactive-client assumptions must not become public logos.
6. Connect the reviewed shared network audit intake and its actual receiver. Add the correct Person/business identity records, profile links and chosen measurement setup through their existing sources. Use supported components; do not rebuild or replace the shared intake merely because a generic template includes a form.
7. Prepare the three source-defined launch articles using actual founder content, truthful reporting examples and maintained method links. Publish the authorized work through the supported source. Check every scoped canonical public route, real 404 behavior, links, phone contact, media, page openings and trade carve-outs; cache-busters alone do not prove the normal page is current.
8. Verify the contact path and intended receiver using the agreed test scope. Save the nine-component coverage, page inventory, source/deployment/rollback state and exact QA evidence. Write the run’s meta article and post the project summary only within the current communication scope. Send any durable improvement to its owning master source for review, then propagate accepted changes.

## Definition of done (QA checklist)

- [ ] The site reflects its actual agency, founder, market, offer and explicit carve-outs.
- [ ] All nine playbook components have meaningful content or precise evidence-backed open items; missing proof is not replaced by filler.
- [ ] Real media, client claims, relationships and service-method links meet the maintained source rules.
- [ ] Ordinary public pages pass the declared first-screen, link, functional and contact checks, with source/deployment state recorded.
- [ ] The actual intake receiver, run write-up and next owner are verified; historical cost, runtime and deployment examples are not presented as current guarantees.

## Example(s)

**Fictional teaching example.** Cedar Trade Marketing serves fence installers and explicitly excludes roofing. Its founder supplies a real interview and approved photos; two clients permit specific case summaries. The nine-part page map includes a founder hero/About, fence services with method links, an industry carve-out page, the two-case client wall, a labeled reporting example, the approved shared audit link, identity/measurement setup and three launch articles. During lesson QA, a template mentions roofing. That defect is removed and rechecked rather than hidden by a high component count. The example is a build plan, not a live agency or two real client results.

Run once per new site or a scoped substantial rebuild. Ongoing reporting, relationships and site reviews use their existing owners and reconciled schedules; this guide does not launch another weekly agent.

## First-run setup and continuity

Open the supplied task file and its linked source. Verify the project’s real inputs, account, access and output folder before work. This Markdown file is a guide; it does not install an app, connect an account, supply a subscription or create a schedule. Carry out work already authorized; do not ask for the same approval again. Keep any unsupplied destination or new action outside that scope clearly pending.

Save source IDs, versions, decisions, checked outputs and next owner in the project tracker. Before a retry, check the saved state and other workers’ changes. A model name does not guarantee memory or a running timer. Repeated work needs an actual configured trigger and durable state; one-off work can be started by the prompt above.

Keep agent media muted with volume zero before playback. If mute cannot be verified, use captions, metadata or still frames. State the limit: silent visual checks do not prove spoken-word accuracy or audio quality. Do not start sound through the user’s speakers unless explicitly asked.
