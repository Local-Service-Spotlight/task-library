# Management (Communicate, Iterate, Delegate)

Help your team finish the right work without late surprises. This guide sets clear owners, early checks and useful next steps. Start with one assigned task and what a good result looks like.

**The path:** Clear assignment → Early check → Small correction → Verified handoff

**Start when:** Work is being delegated or an existing assignment needs a reliable feedback loop.

## Inputs

- The task’s goal, source recipe, pass criteria and current work.
- A real owner, agreed due date, review channel and person authorized to judge the result.
- Previous feedback and the scope each person or AI worker can actually carry.

## Steps

1. Communicate the result, inputs, allowed actions, deadline and check method. Ask the receiving owner to confirm the assignment or name the missing input; do not infer acceptance from a sent message.
2. Agree a useful status cadence for this task: result shipped, blocker and next step. A missed report is unknown state to resolve, not proof that no work occurred.
3. Review a small representative draft early, around the source’s 10% teaching point when useful. Use the real deliverable and checklist to test direction before expensive work.
4. Give specific corrections tied to evidence. Separate a one-off execution error from a defect in the recipe; save the changed draft and confirm the correction actually addressed the issue.
5. Delegate a bounded next scope based on demonstrated results. Access, sending, publishing and spending authority remain explicit; a model name or a good draft does not establish them.
6. When feedback repeats, inspect its cause and propose a maintained-guide improvement. Record the actual accepted change and check its effect in a later run rather than treating an edit as proof of improvement.
7. Close only when the saved result meets the checks and reaches the next owner. Track real rework and turnaround against comparable prior tasks without claiming that more delegation always means better results.

## Definition of done (QA checklist)

Quality assurance (QA) means checking the result against its agreed requirements; see the [Article Guidelines](https://localservicespotlight.com/article-guidelines/).

- [ ] The assignment has an accepted owner, scope, deadline and pass criteria.
- [ ] Early review and corrections have actual saved evidence.
- [ ] Handoff and any responsibility change are confirmed; unresolved work stays visible.

## Start with an agent

Give the AI worker this recipe, the real Inputs, the desired result and the actions already authorized. Ask for the saved output, source evidence, passed and failed checks, and the next owner. A skill is a set of instructions. Loading it does not prove access, install a scheduled job or complete the work. Use the [current installation guide](https://localservicespotlight.com/install/) only if reusable setup is needed; a ZIP contains instructions and is not an access grant.

Use the actual supported app and verified source access. A model name is not a promise of browser control, memory or unattended work. For recurring work, inspect the real job’s trigger, owner, timezone and observed firing; this recipe creates no schedule. Before any media playback, mute the player and set volume to zero. A silent review does not prove sound was heard.

## Record the real execution

Open the run record when work begins. Keep one execution ID, the exact starting recipe revision, input sources and actual state. Write a [meta article, the record of one real execution](https://blitzmetrics.com/meta-article-prompt/) with results, checks, failures and next owner. Link it to this task in the [Task Library](https://local-service-spotlight.github.io/task-library/). Writing is required; public release follows existing authority.

Reuse the same execution ID for internal reviews, meta writing, revisions and retries. A blocked run stays open with its dependency and owner, without an invented finish time. Keep historical public examples as dated evidence; article counts alone are not verified execution frequency. Use supported findings to propose and verify a recipe improvement.
