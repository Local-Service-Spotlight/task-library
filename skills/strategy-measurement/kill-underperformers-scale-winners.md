# Kill underperformers, scale winners

Put ad funds behind results you can prove. This guide helps your team stop weak tests and make small changes to strong ones. Start with the checked facts, test limits and actions you are allowed to take.

**The path:** Checked diagnosis → Exact change plan → Authorized action → Readback

**Start when:** A test’s agreed review window has closed and an evidence-backed pause or scale decision is due.

## Inputs

- [Diagnose weak results](https://local-service-spotlight.github.io/task-library/?task=analyze-why-underperformers-fail#task-analyze-why-underperformers-fail) and the winners list with source metrics and sufficient evaluation windows.
- [Goals, Content, Targeting: the result, proof and people for this work](https://blitzmetrics.com/gct-business-strategy/) targets, existing spend authority and the account’s applicable campaign rules.
- Current ad IDs, budgets, audience settings and prior changes; a supported account editor and change owner.

## Steps

1. Recheck the current account and evidence. Confirm result definitions, conversion delay, sample limits and any recent edits. Do not treat an unresolved source problem as proof that a campaign failed.
2. For each evaluated weak test, propose a pause or one bounded repair using the agreed stop rule. Preserve the asset and history; pausing an ad is not deleting its source page. Document why a retry is justified or exhausted.
3. For a winner, confirm the result still meets its target at useful volume. Prepare a gradual increase or a new audience test with explicit amount, total cap, end/review date and owner. The source’s small [Dollar a Day, small paid tests of proven content](https://blitzmetrics.com/dollar-a-day/) tests are a method, not a universal platform budget guarantee.
4. Check the current provider’s budget and delivery rules. Do not claim a twofold increase is always safe or that every edit resets learning. Google’s [budget-change guidance](https://support.google.com/google-ads/answer/10487143?hl=en) explains that a day’s spending limit can reflect its highest selected daily budget.
5. Apply only the exact changes covered by existing authority through the supported account workflow. If authority or required evidence is missing, save the plan and name the blocker. Freed budget may remain unspent; it is not permission to increase another campaign.
6. Read back the changed IDs, status, budget and schedule. Keep before/after evidence and the actual save time; a proposed action or successful click alone is not a verified change.
7. Set the agreed review condition and compare the resulting performance after adequate data arrives. Carry every pause, test and scale result into the next report, including failures or no action.

## Definition of done (QA checklist)

Quality assurance (QA) means checking the result against its agreed requirements; see the [Article Guidelines](https://localservicespotlight.com/article-guidelines/).

- [ ] Each decision has a target, sufficient evidence and an exact bounded action.
- [ ] Only authorized changes occurred and readback matches the plan.
- [ ] Budget totals, test limits and next review are recorded; no profit or guaranteed scaling claim is made.

## Example(s)

**Fictional teaching example. This is not a client result or proof of a completed run.**

In a fictional account, a reviewed $7 test misses its agreed goal and is paused. Another passes, so the team prepares a $30 test spread over 30 days. The owner has not authorized that new spend yet; the scale remains a proposal. The unused $7 limit is not silently moved elsewhere.

## Start with an agent

Give the AI worker this recipe, the real Inputs, the desired result and the actions already authorized. Ask for the saved output, source evidence, passed and failed checks, and the next owner. A skill is a set of instructions. Loading it does not prove access, install a scheduled job or complete the work. Use the [current installation guide](https://localservicespotlight.com/install/) only if reusable setup is needed; a ZIP contains instructions and is not an access grant.

Use the actual supported app and verified source access. A model name is not a promise of browser control, memory or unattended work. For recurring work, inspect the real job’s trigger, owner, timezone and observed firing; this recipe creates no schedule. Before any media playback, mute the player and set volume to zero. A silent review does not prove sound was heard.
