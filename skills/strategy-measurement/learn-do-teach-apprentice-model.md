# Learn, Do, Teach apprentice model

Help a teammate learn a job well enough to show someone else. This guide turns reading into practice and checks the work at each step. Start with one real task, its guide and a person who can review the result.

**The path:** Learn the method → Do checked work → Teach another person → Verify

**Start when:** A learner is building competence in one scoped task and a qualified reviewer is available.

## Inputs

- One canonical task recipe, its current revision and relevant real examples.
- An authorized practice task with real inputs and safe limits; a capable reviewer and later learner.
- [Learn, Do, Teach](https://blitzmetrics.com/learn-do-teach/) source and the task’s actual quality checks.

## Steps

1. Define the skill to learn and its observable pass criteria. A learner status or a completed document is not evidence of task competence.
2. Learn: read the recipe and proof examples, then explain the method and expected result back to the reviewer. List questions and source gaps before dependent actions.
3. Do: execute a bounded, authorized real task using the guide. Agree an early direction check before the full build and retain inputs, output and actual reviewer feedback.
4. Correct defects and repeat suitable practice until the agreed competence evidence is met. This library’s prior checklist asks for two consecutive clean real runs; keep that as an explicit local training gate, not a universal number claimed by the framework.
5. Teach: help another learner perform the task from the same maintained guide. Observe that learner’s result against the checks. Writing a lesson or meta article alone does not prove the second person learned the task.
6. Record each actual execution and the learner’s current stage, including incomplete teaching. The reviewer decides any change of review duty or responsibility; a successful demonstration does not grant new account access.
7. Use recurring questions to improve the recipe through its existing review process. Write each real run’s meta article; any public example requires separate release authority.

## Definition of done (QA checklist)

Quality assurance (QA) means checking the result against its agreed requirements; see the [Article Guidelines](https://localservicespotlight.com/article-guidelines/).

- [ ] Learning questions and actual practice evidence are retained.
- [ ] The agreed clean-run gate and the next learner’s result are verified or explicitly unfinished.
- [ ] Training status and responsibility reflect the reviewer’s real decision.

## Start with an agent

Give the AI worker this recipe, the real Inputs, the desired result and the actions already authorized. Ask for the saved output, source evidence, passed and failed checks, and the next owner. A skill is a set of instructions. Loading it does not prove access, install a scheduled job or complete the work. Use the [current installation guide](https://localservicespotlight.com/install/) only if reusable setup is needed; a ZIP contains instructions and is not an access grant.

Use the actual supported app and verified source access. A model name is not a promise of browser control, memory or unattended work. For recurring work, inspect the real job’s trigger, owner, timezone and observed firing; this recipe creates no schedule. Before any media playback, mute the player and set volume to zero. A silent review does not prove sound was heard.

## Record the real execution

Open the run record when work begins. Keep one execution ID, the exact starting recipe revision, input sources and actual state. Write a [meta article, the record of one real execution](https://blitzmetrics.com/meta-article-prompt/) with results, checks, failures and next owner. Link it to this task in the [Task Library](https://local-service-spotlight.github.io/task-library/). Writing is required; public release follows existing authority.

Reuse the same execution ID for internal reviews, meta writing, revisions and retries. A blocked run stays open with its dependency and owner, without an invented finish time. Keep historical public examples as dated evidence; article counts alone are not verified execution frequency. Use supported findings to propose and verify a recipe improvement.
