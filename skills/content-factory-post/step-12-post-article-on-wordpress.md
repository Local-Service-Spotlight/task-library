# Step 12: Post article on WordPress

Put your checked article on the right live page. Check where the site saves its pages first, so your work reaches readers. Use the [article guidelines](https://localservicespotlight.com/article-guidelines/) to check the draft before this step.

**The path:** Check site and edit path → Confirm WordPress fits → Save the right record → Check the public result.

**Use this when:** A source-checked article has finished Process, and current site records confirm that WordPress is its approved editor. A page that was once made in WordPress may now be served as fixed files. Those sites need their own recorded source and release path.

## Before opening an editor

First confirm the site, the current source of edits, your allowed action and the tool that can perform it. Keep a dated record of the evidence. A saved login is not proof that this is still the right editor.

| What the current evidence shows | What to do next |
| --- | --- |
| Live WordPress is the approved edit path | Follow the WordPress steps below using the existing authorized tool. |
| A static site serves fixed files, including old WordPress content | Use that site's maintained source and reviewed release process. Stop the WordPress steps here. |
| The site uses another source, such as Astro | Use its maintained source, preview and authorized deployment process. A source merge alone is not a live release. |
| The runtime, source or allowed action is unknown or conflicts | Keep checks read-only. Save the exact missing evidence and existing responsible owner. Do not guess a login or ask for a password. |

A 404 means a route was not found; it does not name the hosting company. WordPress-looking HTML, media paths or sitemaps can remain after a static export. Check a working public page and its response headers, then confirm the edit path in the site's maintained records. A retained WordPress origin may be only a backup. Its existence does not grant permission to edit or publish from it.

For LSS fleet work, use the current website preflight, relationship record, exact domain record and release instructions. Keep those private records private. Do not bypass a held production step, copy the public static site back onto itself, or invent a deployment command. Continue unrelated authorized work while the missing site-specific evidence is resolved.

## Inputs
- The final source-checked article, [Goals, Content, and Targeting](https://blitzmetrics.com/gct-business-strategy/) brief, visual, rights, links, and video/transcript review evidence.
- The exact site and existing article URL/ID if any, page role, author, intended categories, and publishing scope.
- Positive evidence that WordPress is the approved editor for this site now, plus access to the supported tool. For an existing Page or builder, identify its real save source and preserve it.
- The media files, approved destination paths, previous revision, and next publisher/reviewer.

## First-run prompt

> Use the exact site, article, source assets and publication scope I provide. First verify the current public runtime and approved edit path. If WordPress is not the approved editor or the evidence is unclear, stop the WordPress steps and name the correct route or missing evidence. Otherwise find the canonical record, preserve its supported editor and URL, place the article, and check layout and links. Complete the already-authorized save or publication. Verify saved data and normal visitor content separately, and report the exact remaining issue.

## Steps
1. Confirm the runtime/edit-path check above passes for WordPress, then search the site and inventory for the canonical page. Update that record when it already owns the topic. For a genuinely new editorial guide, use a Post and the block editor where appropriate. Preserve an existing Page, builder, URL and supported source; do not rebuild it solely to fit this task.
2. Save the current source and key fields before an update. Check again before saving so a newer edit is not overwritten. Keep the title, date, author and URL unchanged unless the work explicitly calls for changes.
3. Place the article in the supported editor. Use one visible H1, clear H2/H3 sections, short paragraphs, and the real speaker’s voice. Confirm the opening says who it helps, why, and the useful result in plain language.
4. Place the article-specific visual early enough to work in the first desktop and phone screen. Add the real media with descriptive alt text and source/permission notes. A hidden featured-image setting or empty colored box does not meet the visual rule.
5. Embed the actual source video when the article depends on it. Use [YouTube captions by default](https://local-service-spotlight.github.io/task-library/?task=enable-youtube-captions-by-default#task-enable-youtube-captions-by-default) for the player settings. Keep previews silent; a pasted watch URL, poster alone, or transcript pane is not the finished player.
6. Verify the pasted body links and named anchors using [entity-linking guide](https://blitzmetrics.com/entity-linking/). Keep owned teaching links, accurate identity destinations, and specific primary proof. For new content, choose a clear stable slug; do not change an established URL just to fit a keyword.
7. Save a draft when the job is staging work. Complete [categories and tags](https://local-service-spotlight.github.io/task-library/?task=step-13-categorize-post-and-add-tags#task-step-13-categorize-post-and-add-tags), [search metadata](https://local-service-spotlight.github.io/task-library/?task=step-14a-configure-rankmath-seo-plugin#task-step-14a-configure-rankmath-seo-plugin), author and link checks as applicable, then run [Check the full article checklist](https://local-service-spotlight.github.io/task-library/?task=verify-all-items-on-blog-posting-checklist#task-verify-all-items-on-blog-posting-checklist). A plugin step is not a reason to replace an existing supported builder.
8. If publication/update is already authorized and applicable checks pass, publish through the supported route without asking again. Read back the saved record, then open the normal public URL on desktop and phone. If a separate cache or static release is needed, continue only when the current site record explicitly approves that exact source and release route. A retained origin save does not clear a production hold. Otherwise keep the prepared change and record public delivery as pending.
9. Log the exact record, revision, saved state, public URL, visual checks and any pending publication layer. A draft preview, successful API response, or cache-busted copy alone is not proof that ordinary visitors see the change.

## Definition of done (QA checklist)

- [ ] Current evidence confirms WordPress is the approved editor; static/unknown sites have been routed or held without a WordPress write.
- [ ] The correct canonical record and supported editor/source are preserved.
- [ ] The article structure, source facts, media and links survive the transfer.
- [ ] The useful lead visual is readable at 1440×860 and 390×844; no sideways overflow or first-load autoplay.
- [ ] Saved draft/published state matches the job, with no unasked URL or content-type change.
- [ ] When publication is in scope, normal canonical visitor content matches the accepted revision or the exact pending layer is recorded.

## Example(s)

**Fictional teaching example — no site was changed.** Maple Cycle has current evidence that WordPress is its approved editor. It already has `/repair-quote/` as a Page built with its site’s supported builder. A new source clip improves the same guide.

The publisher keeps the Page and URL, saves the old source, replaces the relevant explanation, and puts the real photo beside the short opening. The draft preview looks correct. After an authorized update, WordPress reports the new text but a normal visitor still sees the old version.

The result is “WordPress saved; public delivery pending,” not “published and verified.” The site’s currently approved release route owns the next step; if that route is not proved, delivery stays on hold. A new duplicate Post would not solve it.

A second shop has a working static homepage, old WordPress media paths and a login 404. That evidence does not identify WordPress.com or justify a CMS password request. The publisher records the observed state and uses the maintained source/release instructions. Without them, the result is a read-only diagnosis and a named missing gate.

## Handoff and Content Factory context

The publisher receives the runtime/edit-path evidence, record ID, source revision, media and check results. For a static or unknown site, the existing site-release owner receives the prepared files, exact missing gate and evidence; no WordPress write or new access request is implied. Staged work proceeds to the specific unfinished Post task. Verified live work proceeds to the agreed distribution tasks; [Final formatting and QA checks](https://local-service-spotlight.github.io/task-library/?task=step-17-final-formatting-and-qa-checks#task-step-17-final-formatting-and-qa-checks) closes the served-page review.

This task serves **Post** in the [Content Factory](https://blitzmetrics.com/content-factory/). Produce supplies the source, Process prepares it, Post places and checks it on the agreed channels, and Promote distributes proven work under its own scope. The task’s actual handoff above defines the next step; list order alone does not create a prerequisite.

## When this runs

Run for an initial article or a defined update. No new schedule or standing publisher is installed by this guide.

## First-run setup and continuity

Use the exact account, source, destination and authority recorded for the job. Carry out publication, messages or repairs already authorized once their required checks pass; do not ask for the same approval again. If an action is outside that scope, finish the authorized work and state the specific remaining need. A login, plugin, or task file does not itself grant new authority.

Keep the latest state, record IDs, revisions and next owner in the project tracker or files. Before a retry, check the current saved/sent/published item to avoid duplicates or overwriting another edit. A model has no guaranteed memory, scheduler or account access just because it is called persistent. A future check needs a configured timer or a named person.

Keep all agent media previews muted with volume zero before playback. If this cannot be verified, use captions, metadata or still frames and state what was not tested. No first-load autoplay is part of these page instructions.
